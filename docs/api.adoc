[#api]
= Find the right API

This map helps you choose a starting module. It describes the current source;
follow your https://github.com/lukewilliamboswell/roc-time/releases[release's API link]
for the exact functions available in your package.

[cols="1,2",options="header"]
|===
| Task | Start with
| Calculate an invoice date | `GregorianDate`, `Calendar.Arithmetic.shift_day`, and an explicit month-end policy
| Find booking availability | `ExactInterval.parse` and `Coverage.complement_within`
| Resolve a named-zone appointment | `ZoneRules.from_database` and `ZoneRules.appointment`
| Page a schedule | `ScheduleDefinition.from_native` or `ScheduleDefinition.from_ical`, then `definition.cursor({ series, window })`
|===

== Exact time and availability

For booking availability, start with `ExactInterval.parse`, project each booking
with `ExactInterval.span`, and build `Coverage`. Use `Coverage.complement_within`
with an explicit opening span to find free windows. Keep an `EventCollection`
when you also need booking identities: coverage merges occupied time and cannot
recover which booking contributed it.

For a single timestamp, `OffsetTimestamp.parse` checks its text and `to_text`
writes the canonical form. A `PosixBoundary` identifies its position on the
timeline; `PosixDelta` represents a displacement between positions.

[cols="1,2",options="header"]
|===
| Task | Modules
| Parse explicit-offset timestamps | `OffsetTimestamp`
| Carry a timeline position or displacement | `PosixBoundary`, `PosixDelta`
| Work with nonempty spans and interval text | `PosixSpan`, `ExactInterval`
| Combine occupied time and find gaps | `Coverage`
| Keep event identities | `EventCollection`
|===

For a finite unordered iterator, `Coverage.from_iter` collects its input before
sorting. For ordered input, append each validated span to `Coverage.SortedBuilder`
with `for` or `for!`. The
booking exchange example uses the list path. The separate ordered stream example
retains its pending span and source when the builder reaches capacity.

== Calendar meaning and interpretation

`Calendar.Date` holds a validated date; `Calendar.Delta` says how far to shift it
in calendar units; `Calendar.Value` can describe a whole year or month. These
are separate types: “June 2026” and “one month later” do different jobs.
Import `Calendar` to access them and `Calendar.Arithmetic` for date calculations.

For invoice dates, start with `GregorianDate` and use `Calendar.Arithmetic` when
advancing a month. Choose the invalid-date policy explicitly: January 31 with
clamping and January 31 with rejection answer different business questions.
Use `Calendar.Value` when supplied precision, such as a whole month, is part of
the meaning rather than an exact date.

A `LocalDateTime` describes what a clock shows. `FixedOffset` places it on a
timeline when you know the offset. `ZoneRules` handles named-zone appointments,
including skipped and repeated times. Selecting all positions in a local day is
a separate question: a skipped day can be empty, and repeated labels can produce
separate pieces of coverage.

Some data sources store a time of day as nanoseconds since midnight, such as an
Apache Arrow `Time64(ns)` column. `Nanosecond.ClockTime` keeps every nanosecond of that
value. `Nanosecond.ClockTime.to_clock` requires an exact conversion.
`Nanosecond.ClockTime.to_clock_with_rounding` takes a rounding policy that
you choose; `split_microseconds` gives the `ClockTime` and the remaining
nanoseconds without loss.

[cols="1,2",options="header"]
|===
| Task | Modules
| Construct and convert civil dates | `GregorianDate`, `Calendar.JulianDate`, `Calendar.Date`
| Preserve supplied precision | `Calendar.Value`, `CalendarDescription.QualifiedValue`
| Advance with an explicit calendar policy | `Calendar.Arithmetic`, `Calendar.Delta`
| Express clock labels and resolve them | `ClockTime`, `LocalDateTime`, `FixedOffset`, `ZoneRules`
| Keep a nanosecond time of day | `Nanosecond.ClockTime`
| Display a Gregorian date or local label in English | `EnglishGregorian`
|===

== Recurrence, import and storage

For reusable timed appointments, `ScheduleDefinition.from_ical` imports a
supported iCalendar definition and `from_native` accepts a native one. Create a
cursor for the start-date window you want, then call `ScheduleDefinition.Cursor.collect`
with work and output limits. A `Limited` batch includes the cursor needed to
continue; keep it with the partial output. xref:schedules.adoc#schedules[Schedules]
explains what the query selects. Use `.stream()` on a pure iterator to drive
effectful export. Handle `Limited` and resume with its cursor. Stream exhaustion
alone does not establish a complete temporal result.

Start with `Recurrence.Date` for date-only rules. The lower-level patterns and
`Recurrence.Timed` are useful when composing selectors or working with starts
without appointment endings; ordinary scheduling need not begin there.

If you're composing execution inputs directly, `ScheduleDefinition.Endings` validates
ending definitions for reuse. The adapters' `prepare` operations and
`ScheduleDefinition.Cursor.from_prepared` expose that advanced path. To retain a declaration
for later queries, keep its `ScheduleDefinition`; prepared execution inputs
aren't a storage format.

[cols="1,2",options="header"]
|===
| Task | Modules
| Generate calendar dates | `Recurrence.Date`, `Recurrence.CalendarPattern`
| Query reusable timed appointments | `ScheduleDefinition`, `ScheduleDefinition.Cursor`
| Compose timed recurrence starts | `Recurrence.Timed`
| Import extracted iCalendar values | `ICalendar.DateRule`, `ICalendar.TimedRule`
| Preserve imported descriptions | `Interchange.EdtfDate`, `Interchange.Ixdtf`
| Explain a supported value | `Explanation`
|===

Use `CalendarDescription.Interval` and `Interchange.EdtfInterval`
for independently described interval endpoints, including unknown and open
ends. They retain those meanings for storage without claiming resolved
coverage. xref:profiles.adoc#archive-interval-descriptions-in-development[The archive interval guide]
shows the distinction and links the new example.

== Developing against main?

The https://github.com/lukewilliamboswell/roc-time/tree/main/package[module source and documentation on main] describe the development API. Generate matching local API documentation with a current Roc nightly:

[source,sh]
----
roc docs package/main.roc --output=.roc-time-tmp/api-main
----

Use documentation matching the package in your application header. Source documentation may describe APIs not yet included in your chosen release.

== Nanosecond engine values

Use `Nanosecond.ClockTime` for a time of day, `Nanosecond.PosixBoundary` for a POSIX epoch
position, `Nanosecond.PosixDelta` for a POSIX coordinate displacement, and
`Nanosecond.LocalDateTime` for a naive civil timestamp. Preserve source unit and
column metadata at the engine boundary. All four support exact conversion
to their microsecond counterparts where representable and an explicit
`Nanosecond.Rounding` policy when precision reduction is wanted.

Use `ZoneRules.inspect_snapshot` for a bounded diagnostic of the validity
and transition count of a rules snapshot.
